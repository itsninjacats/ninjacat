# The NinjaCat server

Rust, one Cargo workspace. One image (`Dockerfile`) holds every program; the command a container
is given says which one it runs.

| program | what it is |
| --- | --- |
| `ninjapaws_<host>` (34) | one intake host each: what the Datadog Agent and the tracers send. `dev/intake-routes.yml` and the chart's `intake.programs` say which host names each serves |
| `ninjapaws_internal` | the panel's API and Datadog's query API, on the internal port; it only reads |
| `ninjapaws_monitors` | evaluates the monitors |
| `ninjapaws_migrate` | applies the ClickHouse migrations and the metrics retention, then exits |

A host being a program of its own is what lets each be deployed, scaled and stopped on its own.
Whatever is in front of them (an Ingress, the dev stack's Traefik) sends each host name to its
program; a program does not look at the host it was sent to.

## Layout

```
proto     the agent's protobuf messages, generated by protogen (`cargo run -p protogen`)
engine    the query language and the monitors, compiled to SQL; knows no HTTP and no driver
anomaly   the anomaly, forecast and outlier algorithms the engine calls
storage   rows, the one insert that stores them, the migrations (schema/migrations)
intake    what every intake host shares (keys, auth, bodies, JSON, raw_payloads, the server)
          and one router per host (src/routers)
api       the programs (src/bin)
cli       a command line for the engine
```

A handler decodes what it was sent and inserts the rows itself, one insert per table, before it
answers; ClickHouse's `async_insert` batches the many small inserts on its side. When ClickHouse
refuses one the sender gets a 503 and sends again.

`intake/tests/golden.rs` replays the golden fixtures (`intake/tests/fixtures`, their README says
what they are) through the router of the host each was sent to, into a scratch ClickHouse built
from the migrations, and compares the rows stored there. `schema/migrations` is applied as it is: an applied
migration is immutable (its checksum is in the ledger), so a mistake is fixed by the next one.

## Commands

```bash
cargo build                    # every program, unoptimised
cargo test                     # ClickHouse and Postgres tests skip when the databases are down
cargo clippy --workspace --all-targets -- -D warnings
cargo build --profile dist     # what the image ships: link-time optimisation across every crate
docker build -t ninjapaws .    # the image; --build-arg PROFILE=dev for a quick one
```

`docker compose up` at the repository root runs all of it with the panel.

## Environment

| Variable | Default |
| --- | --- |
| `DATABASE_URL` | required (not by `ninjapaws_install`): the same `postgres://` URL the panel uses (without TLS) |
| `CLICKHOUSE_HTTP_ADDR` | `localhost:8123`, the HTTP interface |
| `CLICKHOUSE_DB`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD` | `ninjacat` |
| `NINJACAT_ADDR` | `:8080`, where an intake program listens |
| `NINJACAT_MAX_BODY_BYTES` | 64 MiB, the largest request body an intake program reads (413 above it); a body may inflate to 64 MiB |
| `NINJACAT_ACK_UNKNOWN` | `true` answers 202 instead of 404 on an unknown path |
| `NINJACAT_LOGS_TCP_ADDR` | `:10516`, the logs program's TCP listener; `off` disables it |
| `NINJACAT_TLS_CERT`, `NINJACAT_TLS_KEY` | PEM files; with both the logs TCP listener speaks TLS |
| `NINJACAT_TRUSTED_PROXIES` | none: the proxies in front of browser-intake whose `X-Forwarded-For` is believed, addresses or networks, comma-separated; the loopback always is |
| `NINJACAT_RUM_ALLOWED_ORIGINS` | any: the origins browser-intake's CORS admits |
| `DEBUG`, `NINJACAT_CAPTURE_DIR` | `true` dumps every intake request to the directory (default `captures`) |
| `NINJACAT_INTERNAL_ADDR` | `:8081`, where `ninjapaws_internal` listens |
| `NINJACAT_QUERY_TOKEN_SECRET` | required by `ninjapaws_internal`: at least 32 bytes, the key the panel signs its tokens with (below) |
| `NINJACAT_METRICS_RETENTION_DAYS` | `30`, days `metrics` keeps raw points; a value outside 1–36500 stops the start |
| `NINJACAT_METRICS_ROLLUP_RETENTION_DAYS` | `400`, days `metrics_1m` and `metric_tag_keys` keep their rows; likewise, and not shorter than the raw retention |
| `NINJACAT_MONITOR_CONCURRENCY` | `8`: loads, evaluations and transition inserts at once in one monitor process |
| `NINJACAT_MONITOR_MAX_GROUPS` | `1000`: the most groups one evaluation may yield; more is an error (`too_many_groups`), never a truncation |
| `NINJACAT_MONITOR_HEALTH_ADDR` | `:8559`: `/health/live`, and `/health/ready` while its lock session is up |
| `NINJACAT_SELFMON_INTERVAL`, `_TENANT`, `_HOST` | `15s`, `default`, the machine's name: the monitor service's own metrics |

`ninjapaws_migrate`, `ninjapaws_internal` and `ninjapaws_monitors` must be given the same two
retentions: the migrating program sets them as TTLs, the other two plan their reads by them.

## The monitor service

Replicas share the monitors through Postgres advisory locks (`shards.rs`): each runs the monitors
of the shards it holds, one of them the notifier, so any number of them works. Postgres holds the
definitions (the panel writes them, with a `pg_notify` in the same transaction); ClickHouse holds
the transitions and evaluations, from which a monitor rebuilds its groups when it moves. The
notifier only records what would be notified (`monitor_notifications`); channels are open work.

## What `ninjapaws_internal` serves (:8081)

| | |
| --- | --- |
| `GET /ping` | liveness |
| `GET /health` | ClickHouse and Postgres reachability; 503 if either is down |
| `GET /api/v1/metrics?from=<unix s>[&host=]` | Datadog's active metrics list |
| `POST /api/v2/query/timeseries`, `/api/v2/query/scalar` | Datadog's v2 query API: queries, formulas, functions |
| `GET /internal/metrics/{names,tags,tag-values,query}` | the panel's metric pages |
| `GET /internal/logs/{search,facets}` | the panel's log pages |
| `GET /internal/checks/names` | the service checks seen |
| `POST /internal/monitors/validate` | checks a monitor in Datadog's JSON with the code the service evaluates with |
| `GET /internal/monitors/status?ids=`, `check-runs` | per monitor: its state and open groups; recent check runs |
| `GET /internal/monitors/{id}/{groups,transitions,evaluations}` | a monitor's groups, timeline and values |

Every route but `/ping` and `/health` asks for `Authorization: Bearer <token>`: an HS256 JWT the
panel signs with `NINJACAT_QUERY_TOKEN_SECRET` for each call (`frontend/src/lib/server/ninjacat.ts`),
with `tenant`, `iss` `ninjacat-panel` and `aud` `ninjacat-query`, valid 60 seconds. The `tenant`
claim is the only source of the tenant. To ask by hand, mint one with the panel's own library (here
for an hour and the tenant `default`; the secret is the dev stack's):

```bash
cd frontend
export SECRET=dev-only-query-token-secret-change-me-32ch
TOKEN=$(bun -e "
import { SignJWT } from 'jose';
const key = new TextEncoder().encode(process.env.SECRET);
console.log(await new SignJWT({ tenant: 'default', role: 'owner' })
  .setProtectedHeader({ alg: 'HS256' }).setSubject('curl')
  .setIssuer('ninjacat-panel').setAudience('ninjacat-query')
  .setExpirationTime('1h').sign(key));
")
curl -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8081/internal/metrics/names?limit=10'
```

**Metrics come from three tables.** `metrics` holds every point, sorted by tenant, metric, the
15-minute bucket, host and series; ClickHouse does not derive the bucket from a condition on
`timestamp`, so every read of it states the bucket as well. `metrics_1m` holds one row per series
per minute, filled by a materialized view: a query whose step is a whole number of minutes reads it,
a finer step the raw points, and a window past the raw retention gets whole-minute steps.
`metric_tag_keys` holds every metric and its tag keys per hour.

## Known deviations from Datadog

Decisions, not gaps:

- **`trace.*` metrics are not metrics here.** APM stats stay in their own table (`apm_stats`) and
  are not merged into the metrics path: a metric query for `trace.*` finds nothing. APM is to be
  queried through its own data sources, not built yet.
- **RUM likewise** stays in its own tables (`rum_events`, `rum_views`, …), queried as events.

## Where Datadog is silent

Wherever behaviour had to be decided that the docs do not pin down, the code says so at that spot:

```bash
grep -rn "WARNING(undocumented)" .   # a choice made; check it against a documented source or a recorded payload
grep -rn "FIXME(" .                   # a choice we doubt
```
